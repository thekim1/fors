Eneo vs. the RAG platform + gateway under load

Both platforms answered from the same 36 support PDFs ("Vanliga fel") with the same simulated model, on the same 4 vCPU server. Eneo ran out of server between 100 and 150 simultaneous users. The RAG platform behind the Ume LLM gateway served 1,000 users with no errors before the server was full.

Eneo v2.3.1 100–150 users

Where the 4 vCPU server is full. At 150 users the first word took 59 s at p95, throughput halved and requests started failing (18 errors over 3 runs).

RAG platform + gateway ≈ 1,000 users

Where the same server is full. At 1,000 users the first word still came in 4.2 s at p95 (the model's own 3 s plus queueing), with 0 errors and 3,167 answers a minute.

How it scales

Eneo v2.3.1RAG platform + gateway

Runs at glm-5.3-flash speed (100, 150, 500, 1,000 users). 150 users is the mean of 3 runs. Eneo was not run at 500 or 1,000: it had already failed at 150.

Why the difference

Eneo puts the whole knowledge base in every prompt

Eneo takes up to context window ÷ chunk size ÷ 2 chunks. With glm-5.3-flash's 1,000,000-token window that is 2,500 chunks, and the 36 PDFs only make 198. So every question sends all of them: about 20,400 prompt tokens. Fetching, counting and assembling them costs Eneo's backend CPU on every question, and the model then has to read them before answering.

The RAG platform sends its top 10 chunks

Retrieval returns the 10 best chunks within a budget of at most 8,000 tokens: about 3,100 prompt tokens per question. Query embeddings are cached, so repeated questions skip that call. Its own share of the first-token time stayed at 15–30 ms until the server was nearly full.

A real provider bills per input token, so with this corpus Eneo's input cost per question would be about 6 times the RAG platform's. That figure is derived from the measured prompt sizes, not measured cost.

Eneo at 150 users

Errors across the three runs: 13 × HTTP 500 (Eneo's generic "Internal server error"), 1 × HTTP 403, and 4 connections closed by the server mid-request. Eneo's backend log had 5, 16 and 21 lines matching database pool or timeout patterns in the three runs, with Postgres at about 135 connections, about 90 of them active.

The likely cause is the backend's database pool timing out while the CPU is saturated, but this isn't confirmed: only the counts were kept that time. run.sh now saves the matching log lines to results/<platform>-errors.log, so a rerun at 150 users would show them.

Setup

The server and the load

  • Each platform is one "server": every container (app, worker, Postgres, Redis, and the gateway on the RAG side) shares 4 pinned vCPUs and memory limits that add up to 18 GB.
  • The fake LLM and the load client run on their own cores, and each run checks that neither was the bottleneck (at 1,000 users they used 1.1 and 0.5 of their 4 threads).
  • Stress load: every user asks again as soon as the 850-token answer has streamed. 30 % of messages are follow-ups in the same conversation; questions come from 42 realistic support tickets, one or two per PDF topic.
  • Only requests started in the measured window count, followed to the end of their stream. Each run starts from fresh databases and re-ingests the PDFs.

The simulated model

  • glm-5.3-flash: 1,000,000-token context window (production's), 850-token answers (the longest support answer).
  • Speed from Artificial Analysis's measurement of Z.ai's API: 3.05 s to first token, 57 tokens/s (run as 17 ms per token, ±30 %).
  • Prompt reading adds 60 ms per 1,000 prompt tokens. This is an assumption: there's no published figure for long prompts.
  • Reasoning ("thinking") is assumed off. With it on, Artificial Analysis measured about 86 s to the first answer token.

Caveats

  • Fake embeddings. The fake model's vectors carry no meaning, so the RAG platform's relevance floor was lifted for this collection: retrieval returns its normal top 10 and the model is always called, as real embeddings would for these on-topic questions. Eneo has no relevance floor, so it was unaffected.
  • Setup by SQL on the RAG side. Its admin API requires a Keycloak sign-in, so the collection, assistant and key were created in the database the way the repo's own dev seed does.
  • Memory limits didn't bind. The test machine (WSL2) has 15.4 GB for Docker, below the 18 GB budget. Neither platform came near it (at most 5.6 GB).
  • Few runs. 150 users was run three times; the others once. The 60-user run used a faster first token (0.4 s), so it isn't directly comparable with the rest.
  • Text-only PDF reading in Eneo. Most of the 113 MB of PDFs are screenshots. Eneo extracts no text from images (198 chunks); the RAG parser uses OCR where needed (248 chunks).
  • The real model's timing decides much of the gap. Faster prompt reading would shrink the cost of Eneo's large prompts; slower would widen it. Eneo's CPU limit at 100–150 users doesn't depend on the model.

Rerun it

Everything is in benchmarks/knowledge-load on the bench/eneo-vs-rag-knowledge-load branch of llmgateway (not merged to main). The README lists the images to build. One run of both platforms takes about 10 minutes:

PDF_DIR=".../Vanliga Fel" VUS=150 HOLD=90 FAKE_TTFT_MS=3050 FAKE_TOKEN_MS=17 \
  benchmarks/knowledge-load/run.sh
python3 benchmarks/knowledge-load/summarize_runs.py results-150   # several runs side by side

Each run's report is committed next to the harness: report-2026-11-17*.md.
